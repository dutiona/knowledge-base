# #629: one store lock, `knowledge-base-ingest remove`, honest backfill counts

Members, one commit each: #596, #578, #595, #579. Synthesized from three lens drafts (mvp-first, risk-first,
architecture-first): the lock, its order and the holder record from risk-first and architecture-first, the one
chunk-deletion owner and #579's pending rule from architecture-first, the trigger and the "at least one vector" rule
from risk-first, and the URL/content-only scope of `remove` and its no-declaration open from mvp-first.

## Outcome

Every KB process that writes a database holds one exclusive advisory lock on `<database>.store-lock`, beside the
database: `knowledge-base` (`--http`, and stdio under owner call O1) for its whole life, every writing
`knowledge-base-ingest` command for its run. A second taker refuses before it reads the database and names the holder
(its role, PID and start time) and the lock file: a server exits 78, a command exits 1. A process releases the lock
only after its job worker has stopped. Read-only commands take no lock, never create or migrate a store (they
refuse a missing or unstamped one) and still run. The kernel releases the lock when its holder dies, so a
killed server leaves nothing to clean, and
the lock works between containers that share the database volume on one host. `knowledge-base-ingest remove
<source_uri>` removes one URL or `content://` document in one transaction: every chunk under it (figures included),
their vectors in every space and every reference to them, through the one chunk-deletion function that reingest, web
and vision also use; its help states what dedup implies. A backfill records each chunk the embedder answers with no
usable vector as refused for that space (schema v3, owner call O2): it is neither counted nor sent again,
`chunk_count` equals the vectors stored, and a space is promotable exactly when nothing is left to embed and it holds
at least one vector, so `re-embed` still promotes over a zero-norm chunk.

## Decisions

**D1. `src/knowledge_base/store_lock.py`, one context manager `hold(db: Path, holder: str) -> Iterator[None]`.**
After memory-engine's `store_lock.rs`, importing only `exceptions`:

- Lock file `Path(f"{db.resolve()}.store-lock")`: symlinks resolved, so every path to one database finds one lock; not
  `.lock`, which SQLite's unix-dotfile VFS uses. The parent directory is created, as `get_connection` does.
- `os.open(lock, O_RDWR | O_CREAT, 0o644)`: never `O_TRUNC` at open, never unlinked (unlinking a held lock file hands
  the next process a fresh inode and a second "exclusive" lock). The descriptor is non-inheritable (PEP 446), so a
  renderer or OmniParser child never keeps a dead server's lock.
- `fcntl.flock(fd, LOCK_EX | LOCK_NB)`: owned by the open file description, released by the kernel however the
  process dies, and two opens in one process conflict, so the suite tests both orders in-process. Never `fcntl.lockf`:
  POSIX locks are per process and drop when the process closes any descriptor of the file.
- `BlockingIOError` → `KnowledgeBaseError` (D3's text); any other `OSError` → `KnowledgeBaseError("cannot lock the
  store {lock}: {strerror}")`; the descriptor is closed on every failure and at the block's exit.
- Deviation from memory-engine: no read-only fallback on `PermissionError`. Every taker writes the database, so a
  process that cannot open the lock file read-write runs as the wrong user, and the holder record needs a writable
  descriptor. It fails naming the path.

**D2. Who takes it, and the order.** Exclusive for every taker.

- `server.main`: arguments → token file and switches (`build_http_app`) → `check_environment()` (pure) →
  `hold(db, holder)` with `db = resolve_db_path()` → `open_declared_db(db).close()` → serve. All of it from the `try`
  on runs inside one `ExitStack`, so a 78, uvicorn's failed start or an in-process `SystemExit` releases the lock.
  After the pure checks, so a misconfigured start leaves no lock file; before the startup gate, which reads and may
  write the store, so a refused start has touched nothing.
- `indexer.main`: the dispatch runs inside `hold(args.db, …)` unless `_read_only(args)`: `status`, `schema`,
  `migrate --check`, `redact` without `--rewrite`. Every other command locks, `remove` and any later command included,
  so an unclassified writer is safe; `test_every_command_is_classified` makes a new subcommand fail until its test
  table classifies it. A refused or misconfigured command can leave the empty lock file, never a database.
- `open_declared_db`, `_conn._get_conn` and the job worker take nothing: they run inside a process that holds it.
- The lock outlives the process's job worker. The worker is a daemon thread that writes independently of the
  transport (`jobs._JobWorker`), and its `stop()` joins for at most 10 s. A new `jobs.shutdown_worker() -> None` sets
  the stop flag and joins without a timeout (the running job ends normally; pending jobs stay `pending` for the next
  start); both entry points call it inside the lock scope on every exit path (the `ExitStack`'s first callback), so
  the lock is never free while this process can still write. A unit's `podman stop` that outlasts its grace period
  ends in SIGKILL, and the kernel then releases the lock with every thread gone.
- Read-only commands never create, bootstrap or migrate a store. `status` and the `redact` report call `init_schema`,
  which bootstraps or migrates an unstamped store, so first they refuse a missing store (`no database at <db>`, as
  `redact` does today) and any store whose `migrate.peek_schema_version(db)` (a `mode=ro` open) is not
  `CURRENT_SCHEMA_VERSION` (`<db> is at schema <n>, this build needs <current>: run knowledge-base-ingest migrate`). On
  a current store `init_schema` returns at once, writing nothing. Their connection stays `get_connection`'s, whose
  `PRAGMA journal_mode=WAL` is a no-op on a store any KB process has opened (every writer opens through it, and WAL
  persists in the file); it would convert only a non-WAL current store that no KB process holds, so it never meets a
  lock holder. Behaviour change: `status` on a missing path no longer creates an empty database.

**D3. The refusal names the holder (#578).** Right after `flock` succeeds the holder replaces the file's content with
one line, `<holder> (pid <pid>, since <UTC %Y-%m-%dT%H:%M:%SZ>)`, `<holder>` being exactly `knowledge-base --http`,
`knowledge-base (stdio)` or `knowledge-base-ingest <command>`: command names only, never argument values (a URL can
carry a password). A refused process reads the first line through its own descriptor and raises `the store is in use
by <line>: <lock> is locked; stop it or let it finish, then rerun` (`another process` when the file is empty). The
line is never a liveness test: only the kernel lock says whether the store is held, so it is not a PID file; a dead
holder's line is overwritten by the next holder. memory-engine names only the lock file; KB says more because #578
asks for the holder.

**D4. Exit codes.** A server refused, or unable to lock: 78 (`EX_CONFIG`), `knowledge-base: <message>`, through the
existing mapping, so a unit with `RestartPreventExitStatus=78` stays down instead of looping. A command: 1 with
`{"error": "<message>"}`, the CLI's existing contract. `remove` of an unknown `source_uri`: 1.

**D5. `remove`.**

- Scope: a `source_uri` starting with `http://`, `https://` or `content://`, after `utils.without_userinfo` (ingest
  stores a URL without userinfo, so a pasted `user:pass@` still matches and is never echoed). Anything else raises
  `ValidationError("… is a file document: reingest replaces it from its file; remove takes URL and content://
  documents")`. A file document has a folder summary and figure images on disk that this command would leave stale.
- Every chunk with that `source_uri`, whatever its `source_type` (a page's figures share it); none →
  `NotFoundError("no document is stored under <uri>")`. One transaction: `delete_chunks_cascade(conn, ids)`, commit;
  any `BaseException` rolls back.
- It embeds nothing, so it opens without a declaration: a `no database at <db>` guard (as `redact`'s), then
  `get_connection` and `init_schema` (which refuses a schema behind or ahead). No job, no folder summary, no file on
  disk (URL and content documents have none), no purge: the text leaves search at once and its bytes stay in free
  pages, FTS segments and the WAL until `knowledge-base-ingest redact --rewrite`, which always purges.
- Prints `{"source_uri": "<as stored>", "chunks_deleted": N}`.
- Help, exact. `help`: `Remove one URL or content:// document and its chunks (server stopped).` `description`:
  `Remove the document stored under SOURCE_URI: every chunk under it, a web page's figures included, their vectors in
  every embedding space and every reference to them, in one transaction. A passage is stored once, under the first
  document that contained it, so a removed document may hold the only copy of a passage a later document also
  contained: that passage then leaves search for both, until the later document is ingested again. The removed text
  stays in the database file until knowledge-base-ingest redact --rewrite purges it.` Argument help: `the document's
  source_uri as search results show it: an http(s) URL (matched without its userinfo) or content://<machine>/<name>`.

**D6. One owner of chunk deletion.** `db.delete_chunks_cascade(conn, chunk_ids) -> int` becomes the only deletion path
and the one place that knows what refers to a chunk: it clears `papers.abstract_chunk_id`,
`relationships.evidence_chunk_id` and `methods`/`datasets`/`metrics.chunk_id`, takes the ids out of
`conclusions.source_chunk_ids` (deleting a conclusion left empty, as today), deletes their `entity_mentions`, then
their vectors in every space (item 3), then the rows (FTS by trigger; `chunk_sessions`, `prediction_errors` and, from
item 7, `embed_refusals` by their foreign keys). It commits nothing; its "callers are responsible for FK cleanup"
docstring goes. `_cleanup_conclusion_refs` moves from `ingest.py` to `db.py` (`db` cannot import `ingest`).
`reingest_file` reads its relink targets (affected papers and named entities) first, then calls it. Redact's
`_merge_into` moves references rather than clearing them and stays as it is.

**D7. #579: the refusal record and one completeness rule.** `_check_promotable` refuses while `chunk_count` is below
the live chunk total, and today the over-count is what lets a space holding a zero-norm chunk be promoted: counting
honestly alone would break `re-embed`. So the store records which chunks the embedder refused for which space.

- Schema v3 (`CURRENT_SCHEMA_VERSION = 3`, `_MIGRATIONS[3] = (add_v3_embed_refusals, False)`, the same function run
  by `db._run_migrations` after `_bootstrap_embed_spaces`, so every origin converges): `embed_refusals(chunk_id
  INTEGER NOT NULL REFERENCES chunks(id) ON DELETE CASCADE, space_name TEXT NOT NULL REFERENCES embed_spaces(name) ON
  DELETE CASCADE, PRIMARY KEY (chunk_id, space_name))`; trigger `chunks_au_refusals AFTER UPDATE OF content ON chunks`
  deleting the chunk's refusals (a refusal judges the text it was given, so `redact --rewrite`'s rewrite is tried
  again); and each space's `chunk_count` set to its table's row count (a space whose table is missing keeps its
  count), repairing stored over-counts.
- A chunk is **pending** for a space when it has the space's `chunk_strategy`, no row in the space's table
  (`v.chunk_id = c.id`, the probe the backfill uses today) and no refusal for the space. The backfill embeds pending
  chunks in id order, selecting `c.content_hash` with each; a `None` vector inserts its refusal (`INSERT OR IGNORE`)
  and logs `chunk <id>: <model> returned no usable vector (zero norm); space <name> records it and will not send it
  again`; `chunk_count` grows by the vectors stored; the result gains `chunks_refused` (`chunks_processed` still counts
  attempts). Each batch writes in one `BEGIN IMMEDIATE` transaction that first re-reads the batch's `(id,
  content_hash)` and writes a vector or a refusal only for a chunk whose hash is unchanged: a stdio server runs tool
  calls on worker threads, so a reingest can delete a batch's chunk while it embeds (a refusal for it would fail its
  foreign key and abort the backfill; a vector for it would be an orphan), and a skipped chunk is simply pending again.
- `_check_promotable(conn, space) -> None` refuses while any chunk is pending (`Cannot promote space <name>: only
  <live - pending> of <live> chunks backfilled (run backfill_space to sync)`), and refuses a space with live chunks
  and no vector at all (`… the embedder returned no usable vector for any of its <live> chunks`): a broken embedder
  must not get an empty space promoted, which today it does. For a deprecated space the pending refusal names the
  supported repair instead (`… <pending> chunks were added or rewritten since it was deprecated; roll back with
  knowledge-base-ingest re-embed`): `backfill_space` takes only populating spaces, so today's "run backfill_space" is
  impossible advice for a deprecated one, and the README's rollback is a re-embed. The deprecated-space staleness
  warning and `promote_space`'s `warning` key go: the pending rule refuses every incomplete space, and the warning
  compared a counter that no longer means "chunks attempted".
- `embeddings.truncate_embedding(vec, target_dim) -> list[float] | None` returns `None` (with the provider's warning)
  for an all-zero prefix instead of raising `ZeroNormError`, which today aborts a Matryoshka backfill at the same chunk
  on every rerun. Its four other callers (`ingest._embed_with_config`, `folder_summaries`, `search`,
  `embed_swap._embed_folder_summaries`) already read `None` as "no vector"; basedpyright checks the new type at each.
- Unchanged: ingest records no refusal; its zero-norm chunk has no vector in the active space, as today.

**D8. Commit order.** The lock first (every later item relies on it: `remove` refuses through it, the v3 upgrade's
`migrate` runs under it), the holder record beside it, then the every-space vector fix, so that `remove` lands with
its whole deletion contract (a removed document leaves no vector in any space) and `chunk_count` already stays exact
across deletions when #579 defines it as the vectors stored; then `remove` with the deletion owner, the figure sites
consolidated onto that owner, the dead-branch cleanup that shrinks the code #579 rewrites, and #579 last: its schema
bump is the one change every existing database must act on.

### Owner calls at approval (Michaël)

- **O1. stdio's lock mode. Recommended: exclusive, like `--http`.** What you see: one `knowledge-base` process per
  database at a time. A second Claude Code session whose KB uses the same database gets no KB tools (its server exits
  78 naming `knowledge-base (stdio) (pid N, since T)`), and writing `knowledge-base-ingest` commands refuse while any
  session is open; several sessions share a database through one `--http` server instead (the infra#81 deployment).
  Why: spec 16's single-writer rule ("KB's CLI resets running jobs when it starts a worker"): every process's job
  worker, on start, resets every `running` job to `pending` (`jobs._run`), another session's included, so two
  sessions can run one job twice; one mode keeps `hold` exactly memory-engine's lock and every refusal able to name
  its one holder. Measured: no `knowledge-base` process runs on this desktop while the fleet's sessions are up, so no
  current workflow loses KB today. *Alternative: shared (`LOCK_SH`) for stdio, exclusive for everything else.*
  Concurrent local sessions keep working as today, and `--http`, the transitions and every writing command still
  exclude them; the job-reset race between sessions stays (it needs its own fix: a job lease), `hold` gains a
  `shared: bool`, a shared holder cannot name itself (the refusal says `another process`), and item 1's
  `stdio-inside-stdio` case becomes an "allowed" case.
- **O2. #579's record. Recommended: the schema-v3 table (D7).** What you see: upgrading to this release needs
  `knowledge-base-ingest migrate` once, unit stopped (it backs up first); until then the server exits 78 naming it, as
  for v2 (#573). Both foreign keys keep it right for free: a deleted chunk (reingest, remove, figure replacement,
  redact's merge) and a cleaned-up space take their refusals with them. *Alternative: a `config` row per space
  holding a JSON list of refused content hashes.* No `migrate`; but no foreign key, so `cleanup_space`, every
  deletion path and redact each keep it, stale entries pile up, the over-counts already stored stay wrong, and the
  row is rewritten whole. Decision touched: #450's versioned schema, extended as v2 was.

### Accepted, not fixed

- `flock` excludes only on one host; never across hosts or on a network filesystem (SQLite's WAL needs a local one
  anyway). Documented.
- A local user who can read the lock file can hold it and block every start; its mode follows the umask, as the
  database's does and as memory-engine's does.
- An MCP client that starts a new stdio KB before the old one has exited sees the new one exit 78. Theoretical; if
  observed, a bounded wait at server start fixes it.
- The upgrade window: the pre-lock server takes no lock, so the first upgrade stops the unit by hand (runbook step 1).
- The pending probe joins vec0's auxiliary `chunk_id` column, as the backfill does today; its speed is unchanged.

**Operator runbook delta (infra#81 owns the runbook; the PR body carries this, nothing here edits it).** The steps
keep their order (stop the unit, run the command through the same image, start the unit); what changes:

1. Upgrading to this release: stop the unit, run `knowledge-base-ingest migrate` once through the new image with the
   db volume (schema v3; it backs up first), start the unit; until then the server exits 78 naming `migrate`. The old
   server took no lock, so this one stop is by hand, as before.
2. A writing command (`ingest`, `reingest`, `ingest-url`, `remove`, `re-embed`, `rebind`, `migrate`,
   `redact --rewrite`) against the running unit, through `podman run` or `podman exec`, exits 1 naming `knowledge-base
   --http (pid …, since …)` and the lock file, having touched nothing: stop the unit and rerun.
3. The unit started while a command runs exits 78 naming that command. The quadlet sets
   `RestartPreventExitStatus=78` (add it if infra#81's does not), so the unit stays down; start it once the command has
   finished. An admin stdio session through the image (`podman run -i … knowledge-base`) holds the lock the same way.
4. Run maintenance containers exactly like the unit: same image tag, `--userns keep-id:uid=10001,gid=10001`, the named
   db volume (a run without it gets a fresh anonymous volume: a new database and a lock nobody else holds), the data
   volume, and the declaration's environment and secret for commands that embed (`remove` needs none).
5. Read-only commands (`status`, `schema`, `migrate --check`, `redact`) take no lock and run against the live unit,
   e.g. `podman exec <unit> knowledge-base-ingest status`. The snapshot recipe is unchanged.
6. `knowledge.db.store-lock` lives on the db volume for good: never delete it (a deleted held lock lets a second
   writer in). After a SIGKILL, an OOM kill or a host crash there is nothing to clean. Its content names the last
   holder and decides nothing. Keep the volume on a local filesystem, on one host.
7. Post-deploy check: with the unit up, an admin `podman run … knowledge-base-ingest rebind` must exit 1 naming the
   unit; exit 0 means the admin run is not on the unit's volume.
8. A mistaken network ingest is removed with `knowledge-base-ingest remove <source_uri>`, unit stopped, instead of
   hand-run SQL; `redact --rewrite` afterwards purges its bytes from the file.
