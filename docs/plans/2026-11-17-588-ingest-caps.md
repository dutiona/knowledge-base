# fix(web): cap ingest_url response size, redirect count and total fetch time (#588)

## Outcome

`ingest_url` and its inline-image downloads read every response body as a stream and stop at a byte cap, follow at
most a few redirects without ever reading a redirect's body, and finish inside one deadline that covers every hop
and every socket operation (connect, TLS handshake, header and body reads). A hostile or huge link fails the call
with an error naming the limit and its variable, instead of exhausting the served KB's memory or holding the call
for minutes. The three limits are operator settings in the environment, checked at startup like the other
`KNOWLEDGE_BASE_*` variables; no tool can change them.

## Constraints

- Issue #588 acceptance, verbatim:
  - "Bodies are streamed and the fetch stops at a configurable cap (a default such as 50 MB), with a clear error naming the cap; the same cap applies to image downloads."
  - "At most 5 redirects (configurable)."
  - "One overall deadline for the fetch, hops included, as well as the per-request timeout."
  - "Tests at the transport layer (the faked network #572 introduces) cover an oversized body, a redirect chain over the limit, and a slow drip that exceeds the deadline."
- "It's an availability problem, not SSRF: #572 keeps every hop on the floor." Every hop stays on `egress_client(floor=True)`; the floor and the pinning are unchanged.
- Michaël, 2026-11-17: "Let's not invent hard rules / hard cap before measuring what it gives us under actual stress." The cap and redirect defaults are the issue's; the deadline default is derived from the measurements below and stays configurable.
- Tests fake the network with `http_requests`, `fake_dns` and `public_net` (AGENTS.md rule 6); no test reaches the internet. Only the socket-level deadline tests use a loopback server, since the faked transport replaces the sockets they exercise.
- KB#573 is in flight on `ingest.py`/`embeddings`; this plan touches neither.

## Measurements (2026-11-17, from the desktop, through today's `egress_client(floor=True, follow_redirects=True, timeout=30.0)`)

| Fetch | Time | Body | Hops |
| --- | --- | --- | --- |
| arxiv abs / arxiv html (1706.03762) | 0.09 s / 0.12 s | 0.04 MB / 0.19 MB | 0 |
| doi.org resolver to arxiv | 0.51 s | 0.04 MB | 1 |
| docs.python.org, MDN, GitHub repo page, httpx docs | 0.08–0.67 s | 0.03–0.26 MB | 0–1 |
| html.spec.whatwg.org (single-page spec, the largest real page tried) | 1.72 s | 16.0 MB | 0 |
| 105 MB test file (proof.ovh.net) | 1.75 s | 104.9 MB | 0 |
| 1 GB test file | 16.56 s | 1073.7 MB | 0 |

Today's `client.get(...)` + `response.text` on the 105 MB file peaks at 336 MiB RSS, and on the 1 GB file at
3107 MiB (baseline interpreter 30 MiB): about three times the body, all held at once. A slow drip is not bounded
at all today: the 30 s timeout is per socket read, so a server sending one byte every 29 s (of the body or of the
headers) holds the call indefinitely, and 20 redirects of 30 s each add about 10 minutes on top.

## Decisions

**D1. Three environment variables, read at call time, validated at startup** (`settings.py`, beside
`host_networks`):

| Variable | Default | Grammar |
| --- | --- | --- |
| `KNOWLEDGE_BASE_FETCH_MAX_BYTES` | `52428800` (50 MiB: the issue's "50 MB" in the binary units the codebase already uses for `_MAX_IMAGE_DOWNLOAD_BYTES` and the 4 MiB HTTP cap) | ASCII decimal integer ≥ 1 |
| `KNOWLEDGE_BASE_FETCH_MAX_REDIRECTS` | `5` | ASCII decimal integer ≥ 0 (0 follows none) |
| `KNOWLEDGE_BASE_FETCH_DEADLINE` | `60` (seconds) | ASCII decimal integer ≥ 1 |

Unset or empty means the default. Anything else (sign, decimal point, non-ASCII digit, zero where ≥ 1) raises
`ValidationError` whose message starts with the variable's name. `check_environment()` calls `fetch_limits()`, so a
malformed value stops the server before the database opens. API: `FETCH_MAX_BYTES_VAR`, `FETCH_MAX_REDIRECTS_VAR`,
`FETCH_DEADLINE_VAR`, `@dataclass(frozen=True, slots=True) class FetchLimits(max_bytes: int, max_redirects: int,
deadline: int)`, `def fetch_limits() -> FetchLimits`.

Why 60 s: the largest real page measured took 1.72 s, and a body at the full 50 MiB cap takes about 42 s on a
10 Mbit/s link. 60 s lets a full-cap body through a slow link and still stops a drip or a redirect chain an order of
magnitude sooner than today.

**D2. The deadline lives in the floored transport, at the socket** (`utils.py`). The per-read timeout cannot carry
it: httpcore captures the read timeout once per response and reuses it for every socket read of the headers and of
the body (`httpcore/_sync/http11.py:170-218`), and `_PinnedTransport` may try several addresses. So:

- `class DeadlineExceeded(Exception)`; `@contextmanager def egress_deadline(seconds: float) -> Iterator[None]` sets
  an absolute `monotonic()` deadline in a `ContextVar` for the duration (nested calls restore the outer value);
  `def deadline_left() -> float | None` returns the seconds left (None outside any deadline) and raises
  `DeadlineExceeded` once none are left. `monotonic` is imported into `utils` so one fake clock drives every check.
- `_DeadlineBackend(httpcore.NetworkBackend)` wraps `httpcore.SyncBackend()`; `_DeadlineStream(httpcore.NetworkStream)`
  wraps each stream it returns. `connect_tcp`, `start_tls`, `read` and `write` pass `min(timeout, deadline_left())`
  to the wrapped call; when the deadline was the tighter bound and the call raises an `httpcore.TimeoutException`,
  they raise `DeadlineExceeded` instead. `connect_unix_socket`, `sleep`, `close` and `get_extra_info` delegate.
  Outside a deadline every call is unchanged, so the LLM, vision and OmniParser clients behave as today.
- `_PinnedTransport.__init__` gives its inner `httpx.HTTPTransport` a pool built with that backend:
  `self._inner._pool = httpcore.ConnectionPool(ssl_context=httpx.create_ssl_context(), max_connections=100,
  max_keepalive_connections=0, keepalive_expiry=5.0, network_backend=_DeadlineBackend())` (the values
  `httpx.Limits(max_keepalive_connections=0)` gave before). `_pool` is httpx's one private attribute used here; the
  loopback socket tests below fail if a release renames it. `HTTPTransport.handle_request` still maps httpcore's
  exceptions; `DeadlineExceeded` is not an httpcore exception, so it passes through httpx and the pool unchanged.
- `_PinnedTransport.handle_request` calls `deadline_left()` before the name lookup and before each address attempt,
  so a hop due after the deadline is never resolved or sent.

The bound: every socket operation of a floored request made under `egress_deadline` ends by the deadline. The one
operation outside it is the name lookup (`socket.getaddrinfo`, which takes no timeout): a lookup that starts before
the deadline can overrun it by the system resolver's own timeout (glibc's default is 5 s per try, 2 tries). Bounding
it would need a lookup thread left running past the call; the plan states the residual instead (D6).

**D3. One fetch helper does the redirects itself** (`web.py`). `_fetch(client, url) -> _Fetched`, with
`_Fetched(body: bytes, url: httpx.URL, encoding: str)` a frozen dataclass and `limits = fetch_limits()` read at the
call. The client is `egress_client(floor=True, timeout=<per-request timeout>)`, redirects not followed by httpx.

1. `request = client.build_request("GET", url, headers={"Accept-Encoding": "identity"})`; everything below runs
   inside `with egress_deadline(limits.deadline)`.
2. Each hop: `deadline_left()`; `response = client.send(request, stream=True)`, closed by a `with`.
3. If `response.next_request` is set (httpx builds it for a 3xx with `Location` when it does not follow, keeping its
   method rewrite, cross-origin `Authorization` stripping, relative `Location` and the request's headers), leave the
   redirect's body unread, count the hop, raise the redirect error once the count exceeds `limits.max_redirects`, and
   continue with `response.next_request`.
4. Otherwise `response.raise_for_status()`; refuse a `Content-Encoding` other than none, `identity`, or exactly one
   of `gzip`/`deflate` (D4); read `response.iter_bytes()`, adding each chunk's length; past `limits.max_bytes`,
   raise the size error; call `deadline_left()` after each chunk and once more after the last. Return
   `_Fetched(b"".join(chunks), response.url, response.encoding)`.
5. `DeadlineExceeded` from any of these becomes the deadline error.

Why not httpx's own `follow_redirects=True, max_redirects=n`: it reads every redirect response's body in full
(`httpx/_client.py:991-992`, `response.read()`), which a 3xx with a multi-GB body turns into the same memory hole.

Compression: the fetch asks for `identity`, so a conforming server sends the counted bytes as they are. A server
that compresses anyway is decoded by httpx (gzip or deflate only; brotli and zstd decoders are not installed, and a
stacked or unknown encoding is refused, since `gzip, gzip` multiplies the expansion). httpx decompresses one raw
socket read (at most 64 KiB, `HTTP11Connection.READ_NUM_BYTES`) at a time, and deflate expands at most about
1032:1, so such a response can overshoot the cap by at most one read's expansion (about 66 MiB) before it is
refused. A decoder that consumes input without producing output cannot stall past the deadline, because every
socket read is bounded by D2.

**D4. Error text** (all `ValidationError`, so the route's `except KnowledgeBaseError` passes them to the tool error
unchanged, and none names the embedder):

- size: `Failed to fetch {url}: the response is over the {max_bytes}-byte cap (KNOWLEDGE_BASE_FETCH_MAX_BYTES)`
- redirects: `Failed to fetch {url}: more than {max_redirects} redirects (KNOWLEDGE_BASE_FETCH_MAX_REDIRECTS)`
- deadline: `Failed to fetch {url}: not done within the {deadline} s deadline (KNOWLEDGE_BASE_FETCH_DEADLINE)`
- encoding: `Failed to fetch {url}: unsupported Content-Encoding {value!r}`

`{url}` is the URL the caller gave, as in today's `Failed to fetch {url}: {e}`, which stays for every other
`httpx.HTTPError` (a per-request timeout that fired before the deadline included).

**D5. The page path.** `ingest_url` keeps its `timeout=30.0` per-request timeout and its URL checks, then calls
`_fetch`; `html = fetched.body.decode(fetched.encoding, errors="replace")` (httpx's own `.text` rule:
`TextDecoder(encoding)` with `errors="replace"`), and `fetched.url` replaces `response.url` wherever it is used.

**D6. Images use the same helper and limits.** Each image download is one `_fetch(image_client, image_url)` with
`timeout=15.0` per request and its own deadline. Any failure (a limit included) logs a warning and skips that image,
as today. `_MAX_IMAGE_DOWNLOAD_BYTES` (10 MiB) is deleted: the issue asks for "the same cap", so the image cap
becomes the configured one (default 50 MiB). Images are fetched only with vision on, which the HTTP server refuses,
so this path is stdio-only.

**D7. Residuals, stated in the docs.**
1. Name lookups are outside the deadline (D2): an overrun of at most one resolver timeout.
2. The Playwright fallback fetches with its own network and timeouts; it is off in the deployment (`--http` refuses
   `KNOWLEDGE_BASE_BROWSER=on`).
3. A page with images, vision on, can spend up to 10 image deadlines after the page's own (stdio only).
4. A server that ignores `Accept-Encoding: identity` can overshoot the cap by one read's expansion (D3).

## Resolution

Review: `docs/plans/2026-11-17-588-ingest-caps-lean-review.md` (Codex, one round). Planning-review severity:
Default, so every finding is resolved.

- **[BLOCKER] The deadline does not bound response headers or every body read; address retries reuse the timeout.**
  Accepted. The deadline moved from per-hop timeout clipping to the socket: D2's deadline-aware network backend
  clips every connect, TLS, read and write to the time left, and `_PinnedTransport` checks it before the lookup and
  each address attempt. Item 2 tests a slow header drip and a slow body drip on a real loopback socket, and the
  two-address case. The DNS exception is resolved explicitly: name lookups stay outside the deadline, bounded by the
  resolver's own timeout, stated as residual D7.1 and raised in the approval handoff.
- **[HIGH] Decoding before counting lets a compressed response exhaust memory.** Accepted. D3: the fetch asks for
  `Accept-Encoding: identity`; a stacked or unknown encoding is refused; a server that sends gzip or deflate anyway
  overshoots by at most one 64 KiB read's expansion (about 66 MiB), stated as D7.4. A decoder making no output cannot
  stall past the deadline, since D2 bounds every socket read. Item 3 tests the header, gzip counting and the
  refusals.
- **[HIGH] A clipped timeout gives the generic error; completion is not checked against the deadline.** Accepted.
  The backend raises `DeadlineExceeded` (not a timeout) exactly when the deadline was the tighter bound, and `_fetch`
  maps it to the deadline error; `deadline_left()` runs once more after the last chunk. Item 2 tests the
  classification both ways; item 3 tests an empty body arriving after the deadline.
- **[MEDIUM] The image test's expected result contradicted itself.** Accepted. Item 4 now asserts one figure, from
  the valid image, with a warning for each skipped image.
- **[LOW] The default-limit test did not establish the defaults.** Accepted. Item 1 asserts the exact
  `FetchLimits(52428800, 5, 60)`, and item 3 tests five redirects followed and a sixth refused with the variable
  unset.
